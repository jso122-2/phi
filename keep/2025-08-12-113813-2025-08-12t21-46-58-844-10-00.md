Training Pipeline (CPU‑safe)
	1.	Split samples into Train/Val/Test (hash by sample_id, 80/10/10; small demo may use 400/50/50).
	2.	K‑kernel mining
	•	Embed Train texts (all‑MiniLM‑L6‑v2, 384D).
	•	Positives: same best_template_match.
	•	Hard negatives: nearest from different template (k≈5).
	•	Light augmentation: token dropout (~0.1–0.15).
	3.	Fine‑tune encoder
	•	Objective = CE (template cls) + NTXent (contrastive), weighted.
	•	Eval metric: Recall@5 on Val (target ≥0.6 for demo).
	4.	Artifacts
	•	Best model → models/thinkerbell-encoder-best/
	•	Embeddings for all (train+val+test) → artifacts/embeddings/encoder_vectors.npy + metadata.jsonl

CLI knobs (defaults reasonable):

--epochs 3 --batch-size 64 --lr 2e-5 --device auto --contrastive-weight 0.5

⸻

Indexing & Retrieval
	•	Normalize L2 vectors; use inner product for cosine search.
	•	FAISS HNSW (if available): dim=384, M=32, efC=200, efS=64.
	•	Fallback (Windows CPU demo): NumPy + sklearn NearestNeighbors (cosine), k=50 then filter.
	•	BONES index = averaged vector per template for template‑only fallback.

Outputs:

faiss_indices/main.index         # if FAISS present
faiss_indices/metadata.pkl       # id -> metadata
faiss_indices/bones.index        # template centroids
faiss_indices/bones_meta.json
artifacts/eval/eval_results.json # acc, R@1/3/5, MRR

Thinkerbell — System Handbook

⸻

1. Project Purpose

Thinkerbell transforms short creative briefs or structured inputs into polished, template-driven documents (e.g., influencer contracts) that look like they were hand-crafted from brand-specific legal templates.

We train on real structured samples, mine semantic patterns, and build retrieval + rendering logic so the system can:
	1.	Detect the most fitting document template.
	2.	Extract or map key fields from the input.
	3.	Generate a fully formatted contract (HTML + optional .docx) with those fields inserted in the right places.

This is not a chat model — it’s a deterministic, dataset-driven doc generator.

⸻

2. Core Components

a) Dataset
	•	Location: synthetic_dataset/
	•	Files: tb_<batch>_<index>.json — ~5000 JSON samples.
	•	Split directories: synthetic_dataset/splits/train, val, test.
	•	Schema:
	•	raw_input.text → full source text
	•	classification → doc type, industry, complexity, confidence
	•	extracted_fields → structured slots (client, campaign, fee, deliverables, exclusivity, etc.)
	•	template_mapping.best_template_match → canonical template ID (profile_*)
	•	validation_scores → semantic + extraction scores

Example Template IDs:

profile_AMAZON _ PBDD Talent Agreement - Jackie Gillies DRAFT
profile_GWM _ WSL CarPool Jack Robinson Agreement_DRAFT
profile_Mattel Brickshop x Craig Contract FINAL.docx LOWNDES SIGNED

⸻

b) K-Kernel Mining

Purpose: Enhance contrastive learning by selecting hard negatives and good positives.

Flow:
	1.	Embed all training texts (all-MiniLM-L6-v2, 384D).
	2.	Positives: Same best_template_match.
	3.	Hard Negatives: Top-k nearest (by cosine) with different template ID.
	4.	Augmentation: token dropout (~12.5%).
	5.	Output: ~3–5x the number of training samples, cached in artifacts/k_kernel/.

⸻

c) Training Loop
	•	Model: SentenceTransformer all-MiniLM-L6-v2
Head: classification for template ID + contrastive loss.
	•	Loss: CE (classification) + NTXent (contrastive) — weighted via CLI flag.
	•	Metrics: Accuracy, Recall@1/3/5, MRR.
	•	Goal for demo: Recall@5 ≥ 0.6 (achieved in last run).

CLI:

python run_training_cycle.py --epochs 3 --batch-size 64 --lr 2e-5 --contrastive-weight 0.5 --device auto

⸻

d) Indexing
	•	Main Index: FAISS HNSW (if GPU or compiled FAISS available).
	•	dim=384, M=32, efC=200, efS=64.
	•	Fallback: NumPy + sklearn NearestNeighbors (cosine).
	•	BONES Index: 1 vector per template (average of all matches).

Outputs:

faiss_indices/main.index
faiss_indices/metadata.pkl
faiss_indices/bones.index
faiss_indices/bones_meta.json

⸻

e) API Endpoints

FastAPI service (api/):
	1.	POST /embed
	•	Input: { text }
	•	Output: { vector, device }
	2.	POST /search
	•	Input: { text, k, filters? }
	•	Output: top-k matches with metadata.
	3.	POST /generate-document  (NEW)
	•	Input: { text, preferred_template? }
	•	Output: { html, plain_text, fields, template }
	•	Steps:
a) Pick template → b) Extract fields → c) Render via stored template skeleton → d) Return HTML contract.
	4.	GET /health
	•	Info on loaded model, index type, counts.
